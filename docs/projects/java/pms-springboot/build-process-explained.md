# PMS Spring Boot 单体版搭建过程讲解

本文结合当前 `pms-springboot` 单体项目的代码，介绍从工程骨架到可运行应用的搭建思路。项目采用 Java 17、Spring Boot 3.2.5、Maven、MySQL 和 Thymeleaf，仅提供服务端页面。独立 REST API 项目位于 [`../pms-springboot-api/`](../../../../versions/java/pms-springboot-api/README.md)。本地环境见[搭建指南](setup.md)，生产运行见[部署指南](deployment.md)。

## 1. 软件需求梳理

搭建应用前，先从使用者、工作场景、数据和运行约束梳理需求。当前需求可以从项目已有的页面、数据结构和权限行为中归纳；它是对现有实现的说明，不等同于经过产品方确认的正式需求基线。

### 1.1 识别用户与使用场景

| 用户/调用方 | 主要目标 | 对应能力 |
|---|---|---|
| 普通用户 | 规划日常执行、回顾每周进展、校准每月投入 | 创建、查看、编辑和删除个人日/周/月清单；查看个人工作台 |
| 管理员 | 管理系统账号 | 查看用户列表并创建用户；不能因此自动读取其他用户的个人清单 |
| 运维人员 | 部署并配置应用 | 配置数据库连接、服务端口和管理员初始账号 |

梳理场景时，要按使用者的完整任务流程描述，而不只列页面名称。例如每日清单的流程是“打开今天的清单 → 填写目标、执行检查和时间盒 → 保存 → 查看进度 → 晚间补充回顾”；每周和每月流程分别侧重周期回顾、计划调整和系统健康检查。

### 1.2 将场景转成可验证需求

需求应描述用户可观察的行为和结果，并为每条需求定义验收方式。按当前项目范围，可归纳为：

| 需求领域 | 当前范围 | 可验证结果示例 |
|---|---|---|
| 日计划 | 记录日期、精力、MIT、检查项、时间盒和晚间复盘 | 用户可新建、修改、查看和删除自己的日计划；同一用户同一天不能重复创建 |
| 周复盘 | 记录下周重点、复盘问题、领域状态和任务流 | 用户可维护自己的周复盘；领域和任务流按所属周记录 |
| 月复盘 | 记录成果、价值判断、改进项和模块健康检查 | 用户可维护自己的月复盘；每个模块在同一月内不重复 |
| 工作台与页面 | 汇总个人周期数据并提供表单页面 | 登录用户看到的是自己的汇总；输入错误时能得到可见的校验反馈 |
| 用户与权限 | 登录、退出、管理员用户管理和个人数据隔离 | 未登录访问受保护页面需先登录；普通用户不能进入管理员页面或读取其他用户记录 |
| 运行配置 | 支持不同环境的数据库、端口和默认管理员配置 | 部署者无需修改源码即可注入环境配置；生产环境不使用示例密码 |

梳理时还要区分功能需求与质量约束：功能需求说明要做什么；安全、数据完整性、可配置性、可维护性则约束功能如何可靠地提供。页面使用 Session，因此需要 CSRF 防护；所有个人记录操作必须以可信的当前用户身份限定范围。

### 1.3 明确边界、假设和待确认项

现有实现支持“个人账号拥有个人清单”和管理员账号管理。它没有表达组织、团队、共享清单、委托访问或跨用户协作关系，因此不能把这些能力当作已满足需求。当前代码也没有定义并发用户数、响应时间、可用性、备份恢复目标、审计保留期等生产服务等级指标；这些数值需要在有明确部署目标时另行确定，不应在讲解文档中臆造。

### 1.4 需求到实现的追踪

每条需求都应能沿着“用户场景 → 页面或 API → 数据模型 → 权限约束 → 验收测试”追踪。比如“不同用户可以有同一天的计划，但不能查看彼此计划”：

1. 用户场景：两个账号分别创建同一天的日计划。
2. 数据设计：`daily_plans` 记录 `user_id`，唯一约束为 `(user_id, plan_date)`。
3. 请求处理：Controller 从当前认证身份取得用户 ID，而不是信任请求正文中的 ID。
4. 数据访问：Repository 在读取、更新和删除时同时匹配记录 ID 与用户 ID。
5. 验收：两个账号均能访问自己的计划；尝试使用另一个账号的记录 ID 时不可读取或修改。

这条追踪方法同样适用于 API 契约、管理员路由、输入校验和子表明细；API 实现位于独立项目。

## 2. 架构设计

### 2.1 架构风格与系统边界

当前项目采用**模块化单体**：服务端页面、业务对象、Repository 和 MySQL 数据在同一个 Spring Boot 应用中运行。REST API 已拆到单独的 `pms-springboot-api` 项目；两者分别部署但共享数据库契约。

系统边界可以概括为：

```text
普通用户 / 管理员
       │ 浏览器请求
       ↓
PMS Spring Boot 单体应用
页面 MVC │ Spring Security
       ↓
Repository / JdbcTemplate
       ↓
共享 MySQL 数据库
```

单体应用负责页面渲染、认证授权和业务数据访问；MySQL 负责持久化及关系约束。API 由独立项目提供。数据库服务和密钥的配置、部署入口以及 HTTPS 终止属于运行环境职责。

### 2.2 模块职责和依赖方向

| 模块 | 职责 | 代码位置 |
|---|---|---|
| Web 入口 | 页面路由、表单 DTO、结果展示 | [`web/`](../../../../versions/java/pms-springboot/src/main/java/com/example/pms/web) |
| 领域对象 | 表达用户、日/周/月记录及其明细 | [`domain/`](../../../../versions/java/pms-springboot/src/main/java/com/example/pms/domain) |
| 数据访问 | 通过 `JdbcTemplate` 执行 SQL、映射结果、管理相关事务 | [`repo/`](../../../../versions/java/pms-springboot/src/main/java/com/example/pms/repo) |
| 横切支持 | 当前用户、页面视图选择、启动初始化等公共能力 | [`support/`](../../../../versions/java/pms-springboot/src/main/java/com/example/pms/support) |
| 安全配置 | Session 登录、角色边界、CSRF 规则和密码编码器 | [`SecurityConfig.java`](../../../../versions/java/pms-springboot/src/main/java/com/example/pms/config/SecurityConfig.java) |
| 页面与静态资源 | Thymeleaf 模板、CSS 和浏览器资源 | [`templates/`](../../../../versions/java/pms-springboot/src/main/resources/templates)、[`static/`](../../../../versions/java/pms-springboot/src/main/resources/static) |
| 配置与表结构 | 环境配置及启动时初始化的 SQL | [`application.yml`](../../../../versions/java/pms-springboot/src/main/resources/application.yml)、[`schema.sql`](../../../../versions/java/pms-springboot/src/main/resources/schema.sql) |

页面请求从 Controller 进入，Controller 负责请求绑定、校验和页面转换，再调用 Repository 读写数据；Repository 将结果组装成领域对象。当前实现没有独立的通用 Service 层，部分业务转换与校验由 Controller 和 Repository 分担。讲解当前架构时应反映这一实际结构，不能将不存在的服务层描述为既有模块。

### 2.3 页面版与 API 版共享业务数据

**页面请求**：浏览器通过表单登录建立 Session → Spring Security 检查登录状态及路由角色 → 页面 Controller 取得当前用户并校验表单 → Repository 按用户 ID 读写数据库 → Controller 将结果放入 Model → Thymeleaf 渲染页面。

页面版只提供服务端渲染入口；需要 REST API 与 Vue 时，使用独立 API 项目。两者沿用相同数据库表与用户数据。

### 2.4 架构决策与取舍

- **单体而非微服务**：日/周/月功能由同一应用和数据库支撑，当前没有独立扩缩容或团队隔离要求；单体减少服务间调用、部署编排和数据一致性成本。
- **页面版与 API 版分开部署**：Thymeleaf 单体满足浏览器表单使用；REST API 位于独立项目并复用共享数据表，避免将页面与 API 入口混在同一项目。
- **JdbcTemplate 而非 ORM**：SQL 与表关系显式，便于遵循多个版本共用的表结构和契约；代价是行映射、查询和字段变更需要显式维护。
- **共享数据库、按用户逻辑隔离**：用户数据保存在同一组业务表，通过 `user_id` 约束所有权；适合当前个人账号模型，但组织/团队隔离出现时需要扩展数据归属模型和权限规则。

### 2.5 关键质量属性如何落实

- **数据完整性**：事务覆盖主表和明细的整体替换；唯一键防止周期重复；外键和级联删除维持主从关系。
- **安全性**：密码使用 BCrypt；页面通过 Session、角色授权和 CSRF 保护；个人业务查询使用所有者条件。
- **可配置性**：端口、数据库连接和凭据通过环境配置注入，避免把特定部署环境写死在业务代码中。
- **可测试性**：纯计算逻辑、日期/枚举处理有单元测试；权限、跨用户访问和完整请求流程可进一步通过应用级测试验证。
- **可维护性**：页面入口、API、数据访问、领域对象和配置各有目录边界；数据库结构变更应使用数据库迁移，而不能依赖仅执行 `CREATE TABLE IF NOT EXISTS` 的初始化脚本。

## 3. 先确定技术分层

项目把职责拆分到不同目录，新增功能时可以沿用下面的依赖方向：

```text
浏览器
        ↓
web：Controller、表单 DTO、请求校验
        ↓
domain：业务数据对象
        ↓
repo：JdbcTemplate 查询和写入
        ↓
MySQL
```

页面由 Thymeleaf 模板渲染，Spring Security 负责页面登录和权限。需要程序化访问时使用独立 API 项目；其 Bearer Token 与单体页面 Session 相互独立，并共用业务数据库。

## 4. 创建 Maven 与 Spring Boot 工程骨架

工程定义在 [`pom.xml`](../../../../versions/java/pms-springboot/pom.xml) 中。Maven 的 Spring Boot parent 统一管理依赖版本，`java.version` 固定为 17。主要依赖各自承担以下职责：

| 依赖 | 用途 |
|---|---|
| `spring-boot-starter-web` | MVC、HTTP 路由和 Web 服务 |
| `spring-boot-starter-thymeleaf` | 服务端页面模板 |
| `spring-boot-starter-security` | 登录认证、授权和 CSRF |
| `spring-boot-starter-validation` | 请求数据校验支持 |
| `spring-boot-starter-jdbc` | `JdbcTemplate` 数据访问 |
| `mysql-connector-j` | MySQL JDBC 驱动 |
| `spring-boot-starter-test` | 测试依赖 |

[`PmsApplication.java`](../../../../versions/java/pms-springboot/src/main/java/com/example/pms/PmsApplication.java) 是应用入口。`@SpringBootApplication` 开启自动配置和组件扫描，`SpringApplication.run(...)` 创建 Spring 容器并启动内嵌 Web 服务器。配置类、Controller、Repository 等组件都位于启动类所在包及其子包内，因此会自动被扫描。

## 5. 配置应用与数据库连接

[`application.yml`](../../../../versions/java/pms-springboot/src/main/resources/application.yml) 集中配置服务端口、MySQL 数据源、页面模板、静态资源、时区、数据库初始化和管理员参数。

配置项使用 `${环境变量:默认值}` 的形式，例如：

```yaml
server:
  port: ${SERVER_PORT:8080}
```

这种写法让开发环境可以直接使用默认值，也可以通过环境变量覆盖。环境变量示例见 [`.env.example`](../../../../versions/java/pms-springboot/.env.example)，正式部署时应更换默认管理员密码，并避免将真实密码提交到版本库。

### `.env` 的加载方式

[`start.sh`](../../../../versions/java/pms-springboot/start.sh) 会先切换到项目目录，再导出 `.env` 中的值，最后执行 `mvn spring-boot:run`。因此：

- 使用 `./start.sh` 时，项目目录下的 `.env` 会被自动加载。
- 直接执行 `mvn spring-boot:run` 或 `java -jar ...` 时，Spring Boot 不会自动读取 `.env`；需要在启动环境中预先设置对应环境变量，或由部署平台注入。

应用使用 MySQL，但启动脚本负责的是启动应用，并不负责安装或启动 MySQL。应先确保 MySQL 服务可用，并创建配置中指定的数据库。

## 6. 定义数据表并初始化

数据表结构在 [`src/main/resources/schema.sql`](../../../../versions/java/pms-springboot/src/main/resources/schema.sql) 中。设计从每日、每周、每月三种业务记录出发，把稳定的主体信息与数量可变的明细拆开，并用外键表达从属关系。

### 6.1 按业务周期划分主表

- `users` 保存账号、BCrypt 密码摘要、显示名和管理员标记。`username` 有唯一键，防止创建重名账号。
- `daily_plans` 保存某个用户某一天的执行计划、13 个勾选项和晚间复盘内容。
- `weekly_reviews` 保存某个用户某周的目标设计和复盘回答。
- `monthly_reviews` 保存某个用户某月的成果、价值判断和改进计划。

日、周、月主体放在不同表中，能让各周期的字段、校验和查询相互独立；周期字段直接参与唯一约束，避免同一用户重复创建同一天、同一周或同一个月的记录。

### 6.2 固定字段与可变明细分开

勾选项和少量问答数量固定，放在各自主表中，读取清单时无需额外连接。条目数量会变化或本身是重复项的内容拆到子表：

| 主表 | 明细表 | 拆分原因 |
|---|---|---|
| `daily_plans` | `time_blocks` | 一天可记录多个时间盒，每项有独立的时间、动作、交付物和完成状态 |
| `weekly_reviews` | `weekly_domain_reviews` | 每个领域单独记录事实和状态，且同一周每个领域最多一条 |
| `weekly_reviews` | `weekly_task_flows` | 任务流条数可变，并按待办、进行中、完成等分桶 |
| `monthly_reviews` | `system_health_checks` | 每个模块独立记录评分和改进项，同一月每个模块最多一条 |

这种拆分避免在主表中预留固定数量的重复列，也避免把一组条目塞进 JSON 或分隔字符串而难以独立校验、查询和更新。子表使用外键指向所属主表；删除主记录时通过 `ON DELETE CASCADE` 清理其明细，避免遗留孤儿数据。

### 6.3 约束、类型和索引各自负责什么

- `PRIMARY KEY` 为每一行提供稳定 ID。
- `UNIQUE (user_id, 日期/周期)` 表达“每个用户每个周期一份”，让数据库在并发请求时也能阻止重复记录。
- 子表的唯一键（例如每周复盘与领域、每月复盘与模块）阻止同一主记录下重复填写相同类别。
- `FOREIGN KEY` 保证明细所属主记录存在，并负责级联清理。
- 日期、时间、数值字段采用 `DATE`、`TIME`、`DECIMAL` 等对应类型；可选内容允许 `NULL`，有合理初值的字段则使用 `DEFAULT`。
- 查询经常使用的用户、日期或父记录字段设置索引，支持列表筛选、周期查询和明细读取。唯一索引本身也可支持相应的唯一性检查和查找。

所有表使用 InnoDB 和 `utf8mb4`，以支持事务、外键和完整的 Unicode 文本。脚本注释中的建库语句用于说明数据库创建方式；应用运行前仍需先创建数据库。

`application.yml` 中的 `spring.sql.init` 配置会在应用启动时执行 classpath 下的 `schema.sql`。建表语句使用 `CREATE TABLE IF NOT EXISTS`，所以重复启动不会重复创建已有表；但它不会为已经存在的表自动新增或修改列，后续结构变更应通过明确的数据库迁移处理。此处需要先创建数据库本身，应用初始化脚本负责创建表，而不是创建 MySQL 数据库。

首次启动时，[`AppInitializer.java`](../../../../versions/java/pms-springboot/src/main/java/com/example/pms/support/AppInitializer.java) 会检查 `users` 表：表为空才按配置创建默认管理员，并使用 BCrypt 保存密码；已有用户时不会再创建默认管理员。

## 7. 建立数据访问与领域对象

[`domain/`](../../../../versions/java/pms-springboot/src/main/java/com/example/pms/domain) 中的类表达业务数据，例如 `DailyPlan` 表示每日计划，包含清单字段、时间盒明细和供页面展示的统计值。

[`repo/DailyRepository.java`](../../../../versions/java/pms-springboot/src/main/java/com/example/pms/repo/DailyRepository.java) 展示了典型的 JDBC 数据访问方式：

1. 通过构造器注入 `JdbcTemplate`。
2. 查询时以用户 ID 限定数据范围，再将查询结果映射为领域对象。
3. 创建或更新计划时，在事务中保存主表和时间盒明细。
4. 编辑明细采用整体替换：先删除旧明细，再写入本次提交的非空行。
5. 组装对象时计算时间盒进度和清单完成数等展示字段。

### 多用户隔离如何贯穿数据链路

该设计使用共享数据库和共享业务表，通过 `user_id` 做逻辑隔离，而不是为每个用户建独立数据库或表：

1. 页面请求由 [`CurrentUser.java`](../../../../versions/java/pms-springboot/src/main/java/com/example/pms/support/CurrentUser.java) 从 Spring Security 的当前认证身份解析用户，并取回数据库中的用户 ID。
2. API 项目从 Bearer Token 中校验签名和过期时间，再根据 Token 的 `uid` 读取用户；不能只相信客户端传来的用户 ID。
3. Controller 将当前用户 ID 传给 Repository。主表的列表、按日期查询、按 ID 读取、更新和删除都同时使用记录 ID 与用户 ID；创建时也把当前用户 ID 写入记录。
4. 明细表不重复保存 `user_id`，而是通过 `daily_plan_id`、`weekly_review_id` 或 `monthly_review_id` 隶属于主记录。业务入口先按当前用户取到主记录，再操作其明细；外键和级联删除保证关系一致。
5. 数据库唯一约束按 `(user_id, 周期)` 组合设置，因此不同用户可以拥有相同日期的记录，但同一用户不能重复创建。

这意味着授权不仅是“是否登录”，也包括“当前账号是否拥有被访问的记录”。即使请求者替换 URL 中的记录 ID，查询仍会因用户 ID 不匹配而无法读取或修改别人的主记录。

## 8. 实现页面请求与模板

页面 Controller 放在 [`web/`](../../../../versions/java/pms-springboot/src/main/java/com/example/pms/web)，模板位于 [`src/main/resources/templates/`](../../../../versions/java/pms-springboot/src/main/resources/templates)。以 [`DailyController.java`](../../../../versions/java/pms-springboot/src/main/java/com/example/pms/web/DailyController.java) 为例：

1. `GET /daily/` 从 Repository 取出当前用户的计划，并放进 Model。
2. `GET /daily/new/` 创建空表单数据，供 Thymeleaf 渲染。
3. `POST /daily/new/` 接收表单 DTO，检查日期、枚举值、数字和时间格式。
4. 校验成功后把表单转换为 `DailyPlan`，交给 Repository 持久化；失败则重新渲染表单和错误信息。
5. 编辑和删除同样根据当前用户 ID 查询或修改，避免通过更换记录 ID 访问别人的数据。

DTO（`web/dto/`）负责承接和验证输入；领域对象负责表示应用中的业务数据。把两者区分开，可以避免直接将页面表单结构绑定到数据库操作。

## 9. 加入登录与权限

[`SecurityConfig.java`](../../../../versions/java/pms-springboot/src/main/java/com/example/pms/config/SecurityConfig.java) 定义页面安全边界：

- 页面默认要求已登录；管理员页面 `/admin/**` 要求 `ADMIN` 角色。
- `/login` 和静态资源对未登录用户开放；业务页面需登录。
- 页面通过表单登录和 Session 维持登录状态，并保留 CSRF 防护。
- 用户密码通过 BCrypt 编码和验证。

API 登录、HMAC Token 和 REST 业务端点由独立的 [`pms-springboot-api`](../../../../versions/java/pms-springboot-api/README.md) 项目提供。

### 安全与多用户设计的边界

- **认证（Authentication）**回答“请求是谁发出的”：页面使用用户名和密码建立 Session。
- **角色授权（Authorization）**回答“当前用户能进入哪些功能”：`is_staff` 用户映射到 `ADMIN` 角色，只有管理员能访问 `/admin/**`；普通登录用户具有 `USER` 角色。
- **记录所有权（Data ownership）**回答“用户能操作哪些业务数据”：每次业务查询或写入都以当前用户 ID 作为条件。这与管理员能否访问 `/admin/**` 是两种不同的权限规则；管理员角色并不自动绕过个人清单的数据归属过滤。
- **浏览器请求防护**：Session Cookie 会随浏览器请求自动携带，因此页面写操作保留 CSRF 防护。
- **密码保护**：数据库存储密码哈希而不是明文密码。
- **输入和数据库约束**：Controller 校验业务输入，JDBC 参数使用占位符绑定，数据库唯一键和外键再提供持久化层的一致性约束。各层职责不同，不能用前端隐藏按钮或只在页面做校验替代服务端授权。

这些措施描述的是应用当前实现的边界；部署时仍应通过 HTTPS 保护登录凭据和 Token 传输，并妥善管理数据库账号与运行环境中的密钥。

## 10. 补充测试并运行

项目测试位于 [`src/test/java/`](../../../../versions/java/pms-springboot/src/test/java)。新增功能时，优先覆盖输入校验、业务计算、权限边界或数据转换等行为。

### 开发环境启动

需要安装 JDK 17、Maven 和 MySQL。先创建数据库（例如 `pms`），再复制并编辑环境变量文件：

```bash
cd versions/java/pms-springboot
cp .env.example .env
# 编辑 .env，填写数据库连接及需要修改的默认凭据
./start.sh
```

访问 <http://127.0.0.1:8080>，首次启动时使用配置的管理员凭据登录。

也可以不使用 `.env`，直接运行：

```bash
mvn spring-boot:run
```

此时请确认数据库等配置已通过 shell 环境变量或其他外部配置提供。

### 执行测试和打包

```bash
mvn test
mvn -B package
java -jar target/pms-springboot-1.0.0.jar
```

打包后的 JAR 可独立运行；生产环境应通过服务管理器注入配置并使用强密码，不要依赖示例默认值。

## 11. 从一个新功能扩展的顺序

以新增一个业务清单为例，建议按以下顺序实施：

1. 先确定主表、明细表、字段类型、可空/默认规则、外键和删除语义。
2. 为用户拥有的数据设计 `user_id` 与周期唯一键，并确定主表与明细表的归属校验方式。
3. 在 `schema.sql` 加建表语句，并保持启动初始化可重复执行。
4. 在 `domain/` 增加业务对象，在 `repo/` 实现带所有者条件的查询、写入和事务边界。
5. 在 `web/dto/` 定义页面输入结构及校验规则，再实现页面模板；API 路由和 DTO 在独立 API 项目中维护。
6. 检查角色授权、页面 CSRF、API 认证和记录所有权过滤，增加对应测试。
7. 运行测试、打包并验证完整请求链路，包括不同用户访问相同周期及尝试访问他人记录的场景。

这条顺序先确定持久化约束，再向上构建请求和页面流程；页面与 API 分开部署但遵循相同的数据契约。

## 12. 通用软件工程策略

下面的策略可用于其他软件项目。PMS 的日/周/月清单、页面与 API 是示例；通用原则是先对齐需求，再选择满足需求的最简单架构，通过小步交付和自动验证控制风险，并根据运行反馈持续改进。

### 12.1 以用户结果和风险确定优先级

1. 先识别用户、主要任务和业务结果，再把需求写成可观察、可验收的行为。
2. 标记范围、假设、外部依赖和未决问题；没有证据的性能或可用性数字不作为承诺。
3. 按用户价值、风险和依赖关系排序。优先验证影响面大或失败代价高的内容，例如数据所有权、认证、数据迁移和外部接口契约。
4. 为需求保留追踪关系：需求对应设计决策、代码变更和测试证据；需求变化时同步检查这些关联。

### 12.2 选择简单且可演进的架构

- 先选择能覆盖当前负载、团队能力和运行约束的最简单方案，不因流行趋势而提前拆分微服务或引入基础设施。
- 明确模块边界、数据所有权和外部契约；跨模块依赖应可理解，持久化和安全边界应由服务端落实。
- 对影响较大的决策记录原因、备选方案和取舍。当业务规模、团队协作或可用性要求改变时，再用实际证据评估是否演进架构。
- 将容易变化的配置与源码分离；对数据库结构变更使用版本化迁移，并制定兼容、备份和回滚办法。

### 12.3 以垂直切片小步交付

以一个用户能完整完成的场景为交付单位，贯穿界面/API、校验、业务逻辑、数据持久化和测试。每次变更尽量聚焦、可审查、可回滚：

1. 为切片写清验收条件和受影响的接口/数据。
2. 先打通最小端到端流程，再补充边界情况和体验改进。
3. 保持代码变更与需求范围一致，不把无关重构混入功能变更。
4. 通过代码评审检查正确性、可读性、安全性和兼容性，合并前处理阻塞问题。

### 12.4 将质量内建到开发流程

测试应与风险相匹配，而不是只在交付前集中补测：

| 验证层次 | 主要关注 | 示例 |
|---|---|---|
| 单元测试 | 纯逻辑、计算、校验边界 | 日期计算、状态转换、进度统计 |
| 数据访问/集成测试 | SQL 映射、事务、约束和组件协作 | 主从表写入、周期唯一键、级联删除 |
| 接口/端到端测试 | 外部可见行为和授权边界 | 登录后增删改查、错误响应、跨用户访问 |
| 发布验证 | 构建产物和部署环境可用 | 启动检查、健康检查、关键用户流程 |

将构建、测试、静态检查和依赖安全检查纳入持续集成；每个质量门都要能给出明确失败原因。测试失败时应修复问题或解释基线差异，不能通过跳过测试或吞掉异常制造“成功”结果。

### 12.5 安全、隐私和数据完整性从设计开始

- 对每个入口识别身份、角色和资源所有权；默认拒绝未授权访问，所有权检查放在服务端数据访问链路中。
- 验证输入、使用参数化数据库操作、最小化收集和返回的数据；秘密信息通过受控配置注入，不提交到源码或日志。
- 按威胁和数据敏感程度选取认证、防伪造、传输保护、审计和保留策略。
- 让数据库约束与业务规则相互补充：应用层提供友好反馈，数据库层保护并发下的数据一致性。
- 设计数据迁移、备份、恢复和删除语义；将破坏性变更视为需要单独评估与验证的发布风险。

### 12.6 让交付可重复、运行可观察

- 使用可重复的构建和部署流程；通过环境变量或密钥管理系统区分开发、测试和生产配置。
- 发布前验证数据库迁移顺序、配置完整性、启动行为和回滚路径；风险较高的变更采用分阶段发布。
- 记录有助于诊断的结构化日志、错误和运行指标，同时避免记录密码、Token 等敏感内容。
- 建立故障处理、备份恢复和依赖升级的责任流程；从线上问题和用户反馈中提炼后续改进项。

### 12.7 建议的完成标准

一个功能可以在以下条件满足后视为可交付：

- 需求范围、验收行为和异常场景已明确，未决事项已记录。
- 设计覆盖数据结构、权限边界、错误处理和接口兼容性。
- 实现遵循既有模块约定，输入校验和服务端授权完整。
- 相关自动化测试通过，构建成功，变更经过评审。
- 配置、迁移、部署和回滚说明已更新；运行风险及后续事项已告知。

这套完成标准不是一次性流程文档，而是团队可以按项目规模裁剪的质量门。小型变更可以合并步骤，但不能省略与风险直接相关的验证。

## 13. 拓展可能性的方案

以下是基于当前个人效能系统的候选方向，不代表现有功能，也不意味着都应立即开发。选择前应先验证真实用户需求、使用频率和维护成本，再按收益、风险和架构影响排序。

### 13.1 三个可独立评估的产品方向

1. **个人流程模板与轻量提醒**
   - 场景：用户经常重复填写相似的时间盒、周计划或月度检查项。
   - 方案：支持保存个人模板、从模板创建新周期清单；确认有提醒需求后，再增加可配置提醒时间和通知渠道。
   - 影响：模板及模板明细需要独立数据结构，并沿用用户所有权隔离；提醒还需要处理时区、重复发送、静默时段和失败重试。
   - 验收例：用户从自己的模板创建清单后可继续修改，模板不会覆盖已有记录；提醒按用户配置触发且不泄漏清单内容给其他用户。

2. **个人趋势与复盘洞察**
   - 场景：用户希望看见精力、时间盒完成情况、检查项和月度健康评分的变化，而不只是逐条查看记录。
   - 方案：先用现有数据生成周/月汇总、趋势图和可解释的回顾提示；早期优先实时聚合，不先引入独立分析数据库或机器学习服务。
   - 影响：需要统一周期口径和缺失数据处理规则，并限制汇总查询只覆盖当前用户；若后续预计算，再设计缓存失效和重算机制。
   - 验收例：用户选择时间范围后，汇总与其明细记录一致；不同用户之间的汇总结果互相隔离。

3. **日历、移动端与外部工具连接**
   - 场景：用户希望在常用日历或移动设备上查看计划、接收提醒，或把数据带到其他工具。
   - 方案：先从只读导出（例如 CSV/iCalendar）或基于现有 REST API 的轻量客户端开始；确认双向同步的真实需要后，再定义同步方向、冲突规则和撤销机制。
   - 影响：需要稳定的 API 版本策略、日期时区规则、外部账号授权与凭据撤销；双向同步还要处理重复请求、并发编辑和冲突合并。
   - 验收例：导出的数据可被目标工具正确读取，且不包含其他用户数据；同步重试不会重复创建记录。

团队/共享清单是另一类高影响方向：它会从“个人拥有记录”扩展成“工作区/团队 + 成员角色 + 共享资源”，不是简单加一个页面。只有在明确共享对象、邀请/退出、管理员权限、成员变更后的数据归属和审计需求后，才建议进入设计。

### 13.2 建议的演进顺序

| 阶段 | 目标 | 建议工作 | 主要风险/依赖 |
|---|---|---|---|
| 0. 演进准备 | 保证后续变更安全可回退 | 建立版本化数据库迁移、关键用户流程与跨用户隔离测试、API 兼容约定 | 当前启动 SQL 适合初次建表，不负责已有表的版本升级 |
| 1. 个人使用效率 | 减少重复输入并支持数据可携带 | 先做模板或个人数据导出，选一个小范围场景验证 | 模板复制应产生独立记录；导出需检查所有者范围和敏感字段 |
| 2. 个人洞察 | 帮助用户发现周期变化 | 增加按用户隔离的趋势汇总与复盘视图 | 指标定义、空周期、数据更正后的汇总一致性 |
| 3. 客户端生态 | 让现有数据可在其他工具使用 | 先提供只读导出或单向集成，再评估移动端和双向同步 | API 版本、凭据管理、时区、幂等与冲突处理 |
| 4. 团队协作 | 支持多人共享目标和复盘 | 单独设计工作区、成员关系、角色和资源归属，再迁移个人数据 | 跨用户授权、数据迁移、成员离开、审计和删除语义 |

阶段顺序是依赖建议而非交付承诺。若用户研究显示团队协作才是核心价值，应先完成团队权限与数据迁移设计，而不是先叠加个人功能。

### 13.3 设计扩展时保持的架构原则

- **先定义需求和验收**：明确目标用户、失败场景、数据范围和不做的内容；对新方向先做小型原型或用户验证。
- **保持纵向切片**：一次交付一个完整且可验证的场景，例如“创建模板 → 用模板创建计划 → 验证数据归属”，避免只铺设空壳抽象。
- **复用现有模块，避免早拆服务**：新能力先沿用当前 Controller、Repository 和部署方式；当独立扩缩容、团队所有权或可靠性要求有证据支持时，再考虑拆分。
- **接口演进保持兼容**：对外 API 变更以共享契约为基线，优先增量扩展；无法兼容时提供版本策略和迁移窗口。
- **数据变更可迁移、可回滚**：每次表结构升级都提供有序迁移、已有用户数据回填策略、备份验证和失败恢复办法。
- **权限从数据模型开始**：新增资源先决定由用户、工作区还是组织拥有，再让查询、写入、导出、后台任务和汇总使用同一授权规则。
- **按需要引入新组件**：只有在验证出技术限制后才增加消息队列、缓存、搜索或分析服务，并记录运行、监控和维护成本。

这样扩展可先从低风险个人能力开始，逐步发展数据洞察和外部连接；需要改变数据所有权的团队协作则作为独立架构项目处理。
