本文把项目现状、已知不足和可继续开发的 Feature 汇总到一个可追溯的路线图中。每个 Feature 使用稳定编号；讨论、拆解任务、实现或验收时应引用编号，并在下方变更记录中登记版本、日期与分支。

## 1. 版本与回溯规则

本仓库包含多个语言、服务模式和前端组合，各组合可以有自己的 release tag。因此：

- **项目发布版本**指对应组合的版本，例如 `java-vue-personal-effectiveness-system-v1.0.0`。
- **本文档版本**是路线图自身的版本，与某个 API 的 Maven/包版本不是同一概念。
- **记录分支**指本次编写和维护路线图的 Git 分支，不代表所有功能只适用于该分支。
- 每次新增、拆分、取消或完成 Feature 时，保留已有 Feature ID，在文档历史中增加一条记录；不要把已发布版本的历史状态直接覆盖。
- 一个 Feature 开始实施时，应在实现分支、PR 和测试记录中引用 Feature ID；合并后更新状态及实际交付的组合版本。

## 2. 当前产品与实现基线

当前核心业务是个人的日、周、月效能闭环：

1. **每日执行**：记录 MIT、精力、执行检查、生活维护、晚间复盘和时间盒。
2. **每周复盘**：回顾工作、学习、身体、关系领域，整理任务流并规划下周成果。
3. **每月重构**：评估目标价值、机会成本、系统健康并确定保留、删减和实验事项。
4. **工作台**：汇总周期记录、近期清单和时间盒完成情况。
5. **多实现组合**：项目有服务端页面版、REST API 和 Vue/React 前端等不同技术组合；API 版本遵循共享契约，数据持久化到 MySQL。
6. **认证与数据归属**：API 版本使用 BCrypt 密码和 Bearer Token；日、周、月数据按当前用户隔离。

本路线图不把尚未开发的事项描述为现有能力。特别是用户管理 API 不等于 Vue/React 已经提供管理员操作界面；本地演示的默认密码和密钥也不能作为生产配置。

## 3. 已知不足与改进方向

以下是当前架构和项目文档中记录的限制。各后端组合成熟度不同，实施前应先确认目标分支及对应代码，不要把 Java API 的具体实现细节直接套用到其他语言版本。

| 编号 | 现状 / 不足 | 影响 | 建议方向 |
|---|---|---|---|
| GAP-01 | 多个列表接口未提供完整的服务端分页和统一过滤 | 数据量增加后响应体和查询耗时上升，前端也难以稳定翻页 | 定义跨 API 一致的分页、日期过滤和排序契约 |
| GAP-02 | 各项目的建表脚本存在启动时初始化逻辑；没有覆盖所有版本的统一、版本化迁移流程 | 修改既有表结构时容易发生版本不一致；启动账号可能需要 DDL 权限 | 分阶段引入 Flyway 或等价迁移机制，并明确 schema 所有权 |
| GAP-03 | API 缺少统一的健康检查、指标、结构化日志和 OpenAPI 文档入口 | 部署、问题定位和接口联调依赖人工查看日志或阅读文档 | 增加安全的 readiness/liveness、可观测性和可生成的接口规范 |
| GAP-04 | Token 有效期内缺少统一的刷新、撤销和会话退出机制 | 泄漏的 Token 可能持续可用到过期；密钥轮换需要额外处理 | 设计跨语言兼容的 Token 生命周期协议和安全存储 |
| GAP-05 | Vue/React 尚未提供完整的管理员用户管理界面 | 用户创建等能力需要调用 API 或使用其他管理方式 | 提供受管理员权限保护的用户列表、创建、停用与重置流程 |
| GAP-06 | 目前没有明确的用户数据导出 / 恢复流程 | 用户迁移、备份恢复和数据可携带性不足 | 定义用户级导出格式、完整性校验与恢复策略 |
| GAP-07 | Dashboard 以当前基本汇总为主，缺少较长时间跨度的趋势分析 | 用户难以比较月度变化或识别长期模式 | 建立可解释的统计指标和趋势视图，避免只追求分数 |
| GAP-08 | 跨语言 API 的一致性主要依赖共享契约和各自测试 | 一种实现变更后，其他实现可能出现字段、状态码或权限语义偏差 | 建立可复用的 API 契约一致性测试 |
| GAP-09 | 默认管理员凭据和开发密钥仅适用于本地演示 | 若部署时未覆盖配置，会产生严重安全风险 | 增加生产启动检查、强配置校验及部署核对清单 |
| GAP-10 | 当前产品边界不包含提醒、日历同步、团队协作等能力 | 用户无法使用外部日程或共享工作流 | 作为新产品 Feature 单独评估隐私、授权和范围，不能视为现有缺陷修补 |

## 4. 待开发 Feature Backlog

### 优先级定义

- **P0**：扩展核心能力前的可靠性、安全性或可扩展性基础。
- **P1**：明显改善日常使用、管理或运维体验的能力。
- **P2**：需要进一步验证用户价值或依赖外部服务的可选扩展。
- **拟议**：尚未评审、未承诺排期；完成条件是验收标准满足并有实现证据。

### P0：可靠性与核心 API

#### FEAT-001 — 跨 API 契约一致性测试

- **目标**：同一组契约测试可验证 Gin、Spring Boot、FastAPI、Flask API 的关键行为。
- **范围**：登录、Token 认证、错误响应、用户隔离、日/周/月 CRUD 和明细整体替换。
- **验收标准**：
  1. 每个 API 实现都可通过相同测试场景或等价的共享测试数据集。
  2. 对状态码、必需字段、JSON 类型和权限边界做断言。
  3. 测试报告能标明失败的 API 实现和 Feature/契约版本。
- **依赖**：稳定的共享 API 契约和可重复的测试数据库。

#### FEAT-002 — 版本化数据库迁移

- **目标**：将生产 schema 更新从“启动时执行建表脚本”过渡到可审计、可排序的迁移。
- **范围**：选择迁移工具；记录基线 schema；规划各语言应用共享数据库时谁负责迁移。
- **验收标准**：
  1. 空数据库可由迁移脚本初始化到当前版本。
  2. 已有 v2 数据库可按顺序升级，且保留现有业务数据。
  3. 应用启动用户不需要无边界的 DDL 权限。
  4. 迁移失败能明确报告版本和错误，不会静默标记成功。
- **依赖**：先盘点所有组合的 schema 差异，明确共享 schema 的唯一维护流程。

#### FEAT-003 — 分页、日期范围与排序

- **目标**：让列表接口在数据增多时仍有稳定响应时间和可预测的资源消耗。
- **范围**：日/周/月列表；统一参数、默认值、边界、排序规则和分页响应格式。
- **验收标准**：
  1. 列表支持页码或游标分页，单页大小有上限。
  2. 支持与业务相关的日期区间过滤和确定性排序。
  3. 多语言实现对参数错误、空结果和总数信息使用一致语义。
  4. 前端加载下一页时不会重复或遗漏记录。

### P1：安全、管理和数据价值

#### FEAT-004 — Token 生命周期管理

- **目标**：提供安全的退出、刷新与撤销机制，并保留多语言互通需求。
- **范围**：短期访问 Token、刷新凭据、登出/撤销、密钥轮换策略和异常会话处理。
- **验收标准**：
  1. 登出后被撤销的凭据不能继续访问受保护接口。
  2. 刷新凭据有独立的有效期和轮换规则。
  3. 不同 API 实现对失效、过期和重放场景有一致响应。
  4. 设计评审明确撤销存储、密钥泄漏应急和跨 API 兼容方案。
- **依赖**：安全设计评审；不可仅延长当前 Token 的过期时间代替撤销。

#### FEAT-005 — 管理员用户管理界面

- **目标**：为现有管理员用户管理 API 提供可用的前端入口。
- **范围**：用户列表、创建用户、显示角色与账号状态；后续再评估停用、重置密码等动作。
- **验收标准**：
  1. 非管理员无法看到或操作管理入口。
  2. 后端继续执行权限检查，不能只依赖前端隐藏按钮。
  3. 表单校验与 API 错误能明确提示用户名冲突和密码要求。
  4. 创建成功后不展示或记录明文密码以外的敏感凭据。

#### FEAT-006 — 用户数据导出与恢复

- **目标**：提升个人数据可携带性和备份恢复能力。
- **范围**：以 JSON 或 CSV 导出当前用户的日/周/月记录及所有明细；恢复功能可另立任务。
- **验收标准**：
  1. 导出内容严格限制为当前用户拥有的数据。
  2. 明细关系、日期、枚举、空值和字符集可无损表达。
  3. 恢复前进行格式和完整性验证，并以事务避免部分导入。
  4. 导出文件提供版本标识，导入工具能报告不兼容字段。
- **依赖**：明确数据格式版本、隐私提示及恢复冲突规则。

#### FEAT-007 — Dashboard 趋势视图

- **目标**：在日/周/月基本汇总之外，提供对长期变化有帮助的可解释视图。
- **范围**：用户可选时间范围；时间盒完成数、清单填写趋势及健康检查分布。
- **验收标准**：
  1. 指标定义清晰，不将“完成率”误作个人价值或绩效评价。
  2. 统计仅包含当前用户数据，边界日期和空数据有测试。
  3. 在有分页或聚合方案的前提下，不要求前端下载全量历史数据。

#### FEAT-008 — 生产可观测性和 API 文档

- **目标**：让部署者能判断应用状态并让客户端开发者查询机器可读契约。
- **范围**：健康端点、结构化日志、请求关联 ID、基础运行指标、OpenAPI 文档。
- **验收标准**：
  1. readiness 能识别必要依赖不可用；liveness 不因数据库短暂不可用而错误触发无限重启。
  2. 健康响应不泄漏数据库地址、凭据、Token 或堆栈。
  3. API 文档与共享契约中的端点、字段、认证方式相符。
  4. 日志不会记录密码、完整 Token 或敏感请求体。

### P2：可选产品扩展

#### FEAT-009 — 提醒与周期通知

- **目标**：帮助用户在自定义时间进行日复盘、周复盘或月重构。
- **前置评估**：用户是否需要浏览器通知、邮件或移动端推送；时区和安静时段如何设置。
- **验收标准**：用户主动启用并能随时关闭；支持时区、频率限制、失败重试和隐私说明。

#### FEAT-010 — 日历集成

- **目标**：允许用户将时间盒导出到常见日历，或在明确授权后同步已有日程。
- **前置评估**：先从单向 ICS 导出验证需求，再评估 OAuth、双向同步和冲突处理。
- **验收标准**：用户可撤销授权；同步范围可控；不会覆盖或删除用户原有日历事件。

#### FEAT-011 — 可访问性和交互一致性

- **目标**：改善键盘、屏幕阅读器和不同屏幕尺寸下的操作体验。
- **验收标准**：关键表单可仅用键盘完成；错误能关联到字段；颜色之外也有状态提示；桌面和移动端主要工作流通过可访问性检查。

## 5. 建议实施顺序

建议先做基础与数据安全，再扩展用户体验：

1. **阶段 A：契约与基线** — FEAT-001、FEAT-002，先明确兼容行为和数据库版本。
2. **阶段 B：核心 API 扩容** — FEAT-003，并用统一契约测试验证各实现。
3. **阶段 C：生产可靠性与身份** — FEAT-004、FEAT-008。
4. **阶段 D：可携带与管理体验** — FEAT-005、FEAT-006。
5. **阶段 E：洞察和外部集成** — FEAT-007、FEAT-009、FEAT-010、FEAT-011；根据用户反馈再排序。

此顺序是依赖建议，不是已批准的排期。具体实施时应为每个 Feature 创建独立任务和验收记录，避免把多个跨栈改动塞入一个无法回溯的大变更。
