## 00:00–01:20｜开场：这套系统解决什么问题

**画面**：标题卡片；随后展示系统工作台和“每日执行、每周复盘、每月重构”三个导航。

**旁白**：

大家好，这段视频会从一个具体业务例子出发，带大家看懂个人效能系统的业务流程、数据结构，以及一次请求最终会经过哪些代码。

这不是单纯的待办清单。它希望解决三个相连的问题：今天优先做出什么成果，一周结束时哪些任务需要继续或退出，一个月之后哪些投入仍然值得。

所以系统围绕三个节奏展开：每日执行、每周复盘、每月重构。我们会重点跟踪“每周复盘里的领域事实”，看一段工作回顾如何从界面进入 API、通过校验、保存到数据库，再返回给页面。

仓库里有 Go、Java、Django、FastAPI 等实现。它们承载相近的业务语义，但页面入口、认证方式和数据访问方式并不完全相同。理解这些边界，是阅读代码时避免把不同项目混为一谈的关键。

**屏幕字幕**：从业务场景出发；沿着输入、校验、保存、输出追踪。

## 01:20–03:30｜业务闭环：日、周、月

**画面**：依次显示每日清单、每周复盘、每月重构卡片；突出每一页的核心字段。

**旁白**：

先看每日执行。用户先写下今天最重要的成果，也就是 MIT，再把工作拆成一个或多个时间盒。每个组块可以记录输入、关键动作、可验收输出、起止时间和是否完成。一天结束后，还可以记录完成了什么、遇到什么阻力、明天从哪里开始，以及值得感谢的一件事。

日清单也包含执行前、执行中、结束后的检查，以及饮水饮食、运动、整理和交流等生活维护项目。系统可以根据时间盒完成情况计算组块进度。

每周复盘往前看一步。用户回顾工作、学习、身体、关系四个领域的事实和状态，整理待办、进行中、已完成、删除或延后等任务流，再为下一周选出最多三项重要成果，并安排深度时间和 If-Then 行动。

每月重构则回到长期方向：本月有什么成果，当前投入是否值得继续，最大的机会成本是什么，接下来准备保留、删减或实验什么。用户还能给六个系统健康模块打分，并写下需要的改变。

这三个节奏不是互不相干的三张表。工作台把今天、本周和本月的记录放在一起，帮助用户从执行走向复盘，再从复盘回到下一轮行动。

**画面提示**：使用箭头动画串起“日执行 → 周复盘 → 月重构 → 下一轮日执行”。

## 03:30–05:20｜代码库里的多种实现

**画面**：展示 `versions/` 目录树，再切换到 Vue 前端目录和数据库 schema 文件。

**旁白**：

接下来要先分清项目目录。Go、Java 和 Flask 都有两种独立项目：一种是服务端渲染的单体页面版，另一种是 REST API 版。Django 是服务端页面应用；FastAPI 提供 REST API，也可以托管 Vue 的构建结果。Vue 本身则独立位于 `versions/vue/pms-vue`。

这意味着，访问页面有两种主要路径。第一种是浏览器直接请求 Go、Java、Django 或 Flask 单体版的服务端页面，由后端生成 HTML。第二种是浏览器运行 Vue 单页应用，再通过 Bearer Token 调用 FastAPI、Gin API、Spring API 或 Flask API。

这些后端实现复用相同的业务数据结构和 API 契约，但不是一个运行时里的六个微服务。它们是可以分别选择、构建和部署的实现。对跨版本协作而言，最重要的连接点是 `db/schema.sql` 的数据结构，以及[REST API 契约](../data/api-contract.md)。

## 05:20–07:10｜示例业务和数据关系

**画面**：屏幕显示示例 JSON，依次高亮 `week_start`、`domains`、`flows`。

**旁白**：

现在进入今天的核心例子。假设本周从二零二六年十一月十六日，也就是星期一开始。用户记录了一条工作领域事实：“完成核心交付”，状态是 `smooth`，并把“整理发布清单”放在进行中。

请求里有三个重要部分。`week_start` 表示周复盘归属的周；`domains` 是领域回顾数组；`flows` 是任务流数组。注意，`work`、`smooth`、`doing` 是稳定的机器可读代码，前端再把它们显示成“工作 / 项目”“顺利”“进行中”等中文。

数据库也把主数据和重复数据分开。`weekly_reviews` 保存周起始日、下周成果、深度时间、复盘问题等主记录；`weekly_domain_reviews` 保存一条或多条领域事实；`weekly_task_flows` 保存任务流。领域表和任务流表都通过 `weekly_review_id` 连接到周复盘。

主表还有两个关键约束：同一个用户同一周只能有一条复盘；同一条周复盘中，一个领域不能重复。明细表的唯一键和外键把这些数据关系落实到数据库层。

**屏幕字幕**：主表 = 一周的复盘；子表 = 多个领域和任务流。

## 07:10–09:00｜第一站：Vue 表单和请求

**画面**：打开 `WeeklyView.vue`，高亮初始化表单、`save()`；再打开 `api.ts` 高亮 `saveWeekly()`。

**旁白**：

先从界面开始。Vue 的每周页面创建新表单时，准备四个领域：工作、学习、身体、关系。用户为每个领域填写事实并选择状态，也可以添加多条任务流。编辑已有记录时，页面会根据服务端返回的记录重新填入这些字段。

按保存之后，`save()` 把表单内容交给 `api.saveWeekly()`。如果没有记录 ID，它发出创建请求；如果有记录 ID，就发出更新请求。请求封装负责把数据转成 JSON，并把当前 Token 放进 Authorization 请求头。

前端类型定义可以帮助开发时保持字段结构一致，但它不能替代服务端校验。用户可能绕过页面直接调用 API，所以日期、枚举、重复记录和数据归属仍然要由后端检查。

从这里开始，完整链路可以概括为：界面采集数据，API 确认身份，输入模型绑定并校验，业务对象转成持久化数据，数据库保存主表与子表，最后再把组装好的响应交回 Vue。

## 09:00–13:20｜第二站：Spring Boot API 的完整处理过程

**画面**：依次展示 `ApiController.java` 的创建 / 更新入口、`WeeklyIn`、`DomainIn` 和 `toWeekly()`。

**旁白**：

我们用独立的 Spring Boot API 追踪。创建请求进入 `createWeekly()`，更新请求进入 `updateWeekly()`。两个入口都会先从 Token 中确认当前用户。

更新比创建多一个关键保护：服务端先按记录 ID 和当前用户 ID 查询现有周复盘。如果这条记录不存在，或属于另一个用户，就返回“记录不存在”，不会继续写入。这个做法让客户端不能通过改 URL 中的数字来读取别人的记录。

随后，Jackson 把 JSON 绑定到 `WeeklyIn`。顶层的 `domains` 对应 `List<DomainIn>`，每个 `DomainIn` 包含领域代码、事实和状态。`safeDomains()` 与 `safeFlows()` 让缺失或 null 的明细数组按空列表处理。`DomainIn` 还有两个简单的空值处理方法：事实为 null 时转为空字符串，状态为空白时默认成 `smooth`。

再往下是 `toWeekly()`。它检查周起始日期能否解析；检查领域代码是不是四种允许值之一；检查状态是不是顺利、受阻或暂停；检查领域是否重复；然后检查任务流分栏是否合法。任何一项不符合，接口会返回四百错误以及对应信息。日期、重复周期等主记录约束也会在保存前核对。

通过校验后，输入 DTO 被转换成 `WeeklyReview` 主记录对象、`WeeklyDomainReview` 领域对象，以及 `WeeklyTaskFlow` 任务流对象。这里要区分三个概念：DTO 描述请求传来的形状；领域对象表达应用准备读写的数据；数据库行才是持久化后的记录。它们字段相似，但职责不同。

**屏幕字幕**：Token 身份 → `WeeklyIn` → 校验 / 转换 → Repository。

## 13:20–15:50｜第三站：保存、事务和重新读取

**画面**：展示 `WeeklyRepository.create()`、`update()` 和 `replaceChildren()`；旁边显示三张数据库表。

**旁白**：

Spring Repository 创建周复盘时，先插入 `weekly_reviews` 主表并取得新 ID，再把这个 ID 赋给领域与任务流明细。更新时，主表的 SQL 会同时带上记录 ID 和当前用户 ID，然后替换明细。

所谓整体替换，是指一次更新提交的 `domains` 数组和 `flows` 数组代表完整的新明细集合。Repository 会删除该复盘原有的领域和任务流，再插入本次提交的内容。因此，空数组代表清空这一类明细，不是保留旧数据。

Spring 的这些 Repository 方法使用事务。主记录写入和明细替换在同一个事务中执行；中间任一数据库操作失败时，事务可以回滚，避免出现主表更新了、明细只写了一半的状态。

保存后，Controller 再按 ID 和用户 ID 读取周复盘。Repository 读取主表，再分别查询两个子表并组装结果。`week_end` 不是用户输入，而是从 `week_start` 加六天得到的派生值。

于是接口返回包含主记录、领域数组、任务流数组和结束日期的 JSON。Vue 收到响应后刷新历史列表；以后编辑时，页面会把返回的领域事实和状态重新放进表单。

**画面字幕**：创建成功 201；更新成功 200；删除成功 204；越权或不存在 404。

## 15:50–18:40｜其他实现：相同业务，不同代码落点

**画面**：四列对照表：Spring API、Gin API、FastAPI、Django 页面；依次高亮各自的输入和持久化位置。

**旁白**：

同一业务在其他实现里位置不同。Gin API 先把 JSON 绑定到 `WeeklyIn`，再由 `normalizeWeeklyIn()` 校验周日期、领域数量、领域重复、枚举和任务流，并填充空状态或序号的默认值。写主表和替换明细的 `InsertWeekly()`、`UpdateWeekly()` 使用 SQL 事务，读回时按记录 ID 和用户 ID 限定范围。

FastAPI 使用 Pydantic 的 `WeeklyIn` 和 `DomainIn` 描述输入字段及枚举。`create_weekly()` 或 `update_weekly()` 从认证依赖取得当前用户，写入主记录，再通过 `_replace_children()` 替换明细，最后由 `weekly_out()` 计算结束日并组装响应。需要特别注意，FastAPI 当前使用自动提交的数据库连接，多个 SQL 操作不天然处于一个事务里。

Django 这里走的是服务端页面，不是共享 API。`weekly_create()` 和 `weekly_update()` 使用一个 ModelForm 处理主表，再用两个 inline formset 处理领域和任务流。保存成功后跳转回页面。用户归属来自 Django 当前登录账号；模板负责把表单和结果呈现给浏览器。

Gin 和 Spring 的单体页面版也走各自的页面 Controller 或 handler、表单、模板和 Session，不提供这套 `/api/weekly` JSON 入口。换句话说，业务字段可以相似，但页面表单地址不能当作 API 地址使用。

还有一个值得保留的细节：Go 和 Spring API 都显式检查重复领域；FastAPI 的 Pydantic 模型约束领域枚举，但没有同等的请求级重复领域检查，数据库的唯一键仍会约束重复值。错误如何被转换，也可能存在差别。因此，跨实现“正常数据都能保存”还不够，重复数据和错误响应也应加入验收。

## 18:40–20:30｜安全、边界和修改顺序

**画面**：展示所有权 SQL 条件 `id + user_id`、schema 唯一键，以及跨版本功能修改流程。

**旁白**：

最后总结三个容易忽略的边界。

第一，用户身份来自经过验证的 Token 或页面 Session。用户数据读写必须始终按当前用户限制，不能相信客户端自己提交的用户 ID。

第二，事务边界不是跨语言自动一致的。Go API 和 Spring Repository 都明确使用事务；Django 页面流程没有显式包在 `transaction.atomic()` 中；FastAPI 的 autocommit 会让主表与子表操作分别执行。遇到数据库错误时，各版本可能留下不同结果，所以要把失败路径测出来。

第三，契约和数据库结构是跨版本同步的起点。增加或修改字段时，先确定业务规则，再更新共享契约和数据模型，接着修改各输入与持久化层，最后更新页面或 Vue 类型，并验证合法数据、非法数据、重复周期、空明细和跨用户访问。

这就是从一个“工作领域事实”一路追踪到代码和数据库的过程：先弄清楚用户为什么填写，再看数据怎么进入系统，最后确认它如何被安全地保存和重新展示。

以上就是个人效能系统的业务与代码追踪。感谢观看，我们下次再见。

**收尾字幕**：业务规则 → API 契约 → 数据结构 → 各实现 → 跨版本验证。
