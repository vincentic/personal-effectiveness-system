## 00:00–04:00｜项目背景与目标

**画面**：标题卡；展示每日、每周、每月三个入口，再切换到桌面与手机界面。

**旁白**：

大家好，欢迎来到个人效能系统的项目介绍。这次我们不只看某一个页面或某一种语言，而是从需求来源开始，完整介绍系统做什么、如何设计、怎样验收，以及上线后如何持续改进。

系统关注的不是把所有待办都堆进一个列表，而是帮助用户形成一个可重复的行动闭环：每日执行、每周复盘、每月重构。用户每天明确最重要的成果，把工作拆成有输入、有关键动作、有可验收输出的时间盒；一周结束后回顾事实和任务流；一个月之后再判断目标、投入和工作系统是否仍然值得。

仓库里保留了不同语言和架构风格的实现。服务端页面应用、REST API 和独立前端是不同的运行方式，不能因为业务名称相同就假设它们都运行在同一个服务里。为了便于评估组合，API 与 Vue、React 前端已经分别整理为八个聚焦分支；主分支仍保留完整多语言项目。

本片会依次讲清产品边界、业务字段、数据所有权、技术组合、验收方法和反馈闭环。涉及尚未实现或尚未验证的内容，会明确标注为规划或验收目标，而不会把目标说成现状。

## 04:00–12:00｜用户需求与功能范围

**画面**：展示需求规格中的用户故事和日、周、月页面。

**旁白**：

首先看用户是谁。知识工作者、学生、自由职业者和需要管理个人节奏的负责人，面对的问题不完全一样，但常见痛点相似：每天很忙却说不出成果，任务越积越多，计划容易排得过满，做完以后又没有复盘。

因此，我们将需求分成六个领域。第一是账户和权限，用户需要登录，数据必须归属于当前账号。第二是工作台，快速看到今天、本周和本月的进度。第三是每日执行，记录日期、睡眠、精力、MIT、执行检查、生活维护、晚间复盘和时间盒。第四是每周复盘，记录工作、学习、身体、关系四个领域的事实和状态，整理任务流，并确定下周最多三项成果。第五是每月重构，记录投入价值、机会成本、保留或删减的事项、实验计划和系统健康评分。第六是多端访问和共享数据，让用户能够选择不同实现而不改变核心数据语义。

这里要说明一个产品边界：现有 Vue 和 React 前端提供登录、工作台、日、周、月流程，但没有用户管理界面。管理员管理用户需要使用对应后端的管理能力。系统也不承诺离线编辑、第三方日历同步、团队协作、消息通知或支付功能。这些都属于未来可以讨论的扩展，不属于当前验收范围。

需求的写法需要能被测试。比如“系统要安全”太宽泛，我们将其拆成具体条件：用户 A 不能读取、更新或删除用户 B 的记录；缺少或过期的 Token 不能访问受保护资源；同一用户同一日期不能重复创建每日清单。对用户来说，这意味着数据不会串号，重复记录会得到解释，而不是出现无法修复的脏数据。

另一类需求是可理解性和效率。每日表单强调一个 MIT 和清晰的交付物；周复盘强调事实，不只写感受；月度重构限制改进项数量，避免把工具本身变成新的负担。桌面和手机界面都要能完成核心操作，不能只是页面缩放后勉强显示。

**屏幕字幕**：需求以用户结果表达，验收以可观察行为判断。

## 12:00–20:00｜业务流程与数据设计

**画面**：用流程图串联日、周、月；再展示 `db/schema.sql` 中的主表和明细表关系。

**旁白**：

业务流程从每日开始。用户创建某一天的执行清单，为时间盒填写任务、输入、动作、可验收输出、起止时间和完成状态。一天结束后，可以补充实际完成、阻力、明天的最小启动动作和感谢事项。工作台展示周期摘要，帮助用户快速回到执行状态。

每周复盘把多个日常事实收拢起来。用户记录四个领域的事实和状态，将待办整理到待办、进行中、已完成、删除或延后等任务流，再设定下周的优先成果和深度工作安排。月度重构继续向上观察，判断当前目标是否值得投入，并通过六个健康模块发现计划过载、恢复不足或复盘质量偏低等问题。

数据模型将主记录和重复明细分开。每日主表关联多个时间盒；周复盘主表关联多个领域事实和任务流；月度记录关联多个系统健康检查。每个主记录都有用户归属和周期键：日记录由用户与日期唯一确定，周记录由用户与周起始日唯一确定，月记录由用户与月份唯一确定。

这种关系有两个直接效果。第一，重复事项可以单独排序和更新，不需要把整条清单塞进一个文本字段。第二，删除主记录时，关联明细可以按照外键规则一起处理。写入更新时，接口约定明细数组表示完整的新明细集合；空数组意味着清空，不是“保留旧数据”。

字段名、状态代码和前端中文显示之间也要保持边界。比如领域状态在 API 中使用稳定代码，页面再显示本地化文案。不要把“进行中”这样的界面文字直接变成数据库唯一依据，否则语言切换会影响数据兼容性。

数据脚本负责初始化缺失的表，并不等同于一套完整的版本迁移工具。已有生产表要增加字段时，必须另行设计迁移、备份、回滚和前后版本兼容，不能只依赖启动时再次执行建表脚本。

## 20:00–31:00｜系统架构与八种组合

**画面**：展示架构图，先分层，再点亮八条“前端 → API → MySQL”路径。

**旁白**：

系统可以按三个层次理解。最上面是用户界面，包括 Vue、React，以及 Go、Spring Boot、Django、Flask 的服务端页面。中间是应用服务：部分实现直接渲染 HTML，另一些实现提供 JSON REST API。最底层是 MySQL，保存账号、日周月主记录和明细。

这不是要求所有项目一起启动的微服务集群，而是一组可以分别选择的实现。服务端页面版通过 Session 和表单处理请求；API 版通过 Bearer Token 识别用户；Vue 与 React 作为单页前端发送 JSON 请求。页面 Session 和 API Token 是两条不同认证路径，不能互相当作同一种凭证。

本次组合发布聚焦四种 API 后端与两个前端。Go Gin API 默认端口是 8081，Spring Boot API 是 8080，FastAPI 是 8000，Flask API 是 8002。Vue 开发端口是 5173，React 开发端口是 5174。开发代理把前端的 `/api` 请求发往所选 API；生产部署则通过 Nginx、Ingress 或同源托管完成路由。

Go API 使用 Gin、`database/sql` 和 SQL store；Spring Boot API 使用控制器、HMAC Token 校验和 JdbcTemplate Repository；FastAPI 使用 Python、Pydantic、Uvicorn 与 PyMySQL；Flask API 使用 Flask、Pydantic 和 PyMySQL。虽然实现工具不同，但对外要共同遵守登录、用户归属、日周月记录结构、请求校验和错误语义。

八个组合分别是 Go 加 Vue、Go 加 React、Java 加 Vue、Java 加 React、FastAPI 加 Vue、FastAPI 加 React、Flask 加 Vue、Flask 加 React。Vue 和 React 都可以与四种兼容 API 配合。在 FastAPI + Vue 组合中，Vue 构建产物由 FastAPI 同源提供；在 FastAPI + React 发布分支中，React 构建产物也配置为由 FastAPI 同源提供。其他组合通常将 SPA 独立部署，再由代理转发 API 请求。

安全边界也要横跨这些层次。密码使用哈希保存，API_SECRET 用于签发和校验 HMAC Token；客户端不能自行决定记录所属用户，服务端必须从凭证中获得当前用户，并在查询、更新和删除时应用所有权条件。生产环境还必须配置强随机密钥、HTTPS、精确 CORS 来源和最小权限数据库账号。

架构上的取舍包括：单体页面适合希望一步部署页面和服务的场景；独立 API 加 SPA 更利于前后端分别发布；FastAPI 同源模式可以减少跨域配置，但构建流程需要把前端产物正确输出到后端目录。每种方式都有维护成本，不应只按语言喜好选择。

## 31:00–39:00｜页面功能与关键操作演示

**画面**：先登录，然后演示工作台、每日、每周、每月页面。录制用虚构账号和数据。

**旁白**：

现在进入一段用户视角演示。登录后先看工作台，它汇总当前周期状态和近期记录。空数据时应有清晰的空状态，而不是看起来像页面加载失败。

每日页面先填写日期、精力和 MIT，然后新增两个时间盒。第一个时间盒写下需要的材料和关键动作，输出填写成能够被核对的结果。第二个时间盒可以代表学习或运动。保存后回到列表检查日期和进度，再进入编辑流程，修改一个输出并勾选完成状态。最后删除演示记录，确认删除后页面没有残留。

每周页面按工作、学习、身体和关系记录事实。请选择一个状态，再添加一条进行中的任务和一条待办任务，填写下周重要成果和 If-Then 计划。保存后重新打开，确认领域数据、任务流和计划字段能够回显。编辑时用完整的新明细集合，观察旧明细是否按约定替换。

月度页面填写本月成果、是否继续投入和机会成本，再给若干健康模块评分，写下保留、删减和实验事项。工作台中的月度均分应只依据已填写的有效分数计算；如果没有评分，应展示空状态，而不是误报为零分。

最后切换到手机宽度，确认登录、导航、表单、明细增删和保存按钮均可操作。响应式布局的验收要实际操作，不只是查看一张截图。录制时使用虚构账号，不展示密钥、真实个人数据或生产数据库内容。

**屏幕字幕**：演示覆盖新增、读取、编辑、删除、移动端和错误反馈。

## 39:00–47:00｜验收、测试与发布管理

**画面**：展示需求追踪表、测试矩阵、CI 结果及 release 分支列表。

**旁白**：

验收管理从需求追踪开始。每项需求应关联到可操作的验收场景、测试数据、执行结果和问题编号。功能层至少覆盖日、周、月新增、读取、编辑、删除、周期唯一性、空明细替换和工作台汇总；安全层覆盖未登录、无效凭证和跨账号访问；界面层覆盖桌面、手机和空状态；交付层覆盖可重复安装、构建、部署和健康检查。

测试不是只有一个“通过”按钮。单元测试适合验证输入转换和状态规则；API 测试验证 HTTP 状态码、字段和权限；数据库集成测试检查外键、唯一键、事务边界与跨账号隔离；浏览器测试则验证实际用户流程。对于当前没有自动化覆盖的部分，要把它登记为待验收，而不是默认通过。

跨后端验收应使用相同的契约测试数据，分别执行登录、读取工作台、创建和修改日周月记录。尤其要检查非法枚举、重复周期、超长字段、空子表和他人记录。各语言对异常的映射可能不同，错误状态和错误语义都需要对照契约检查。

发布管理可以以八个聚焦分支作为可交付单元：分支名明确表示后端与前端组合，每个 Release 有自己的 tag 和安装说明。主分支保留完整多语言项目。发布前应记录 commit、版本、数据库兼容要求、配置项、构建结果、已知问题和回滚办法。数据库变更要先兼容旧版本，再逐步切换应用，不能只发布代码而忽略数据结构。

目前已验证的是指定的前端构建和部分后端测试；真实 MySQL 集成、生产环境恢复演练、压测和安全评审不能仅凭构建结果宣称完成。建议在验收记录中分为“已自动验证”“人工验证”“待环境验证”三类，保持事实透明。

## 47:00–52:00｜收集反馈与持续改进

**画面**：展示反馈问卷示例：用户场景、问题步骤、期望结果、实际结果、设备与版本。

**旁白**：

反馈流程不是现有应用内置的收集功能，而是建议在试用和发布阶段配套执行。可以邀请少量代表用户完成三个任务：建立每日计划、完成一次周复盘、查看月度重构。结束后不要只问“好不好用”，要记录用户实际做了什么、在哪一步犹豫、是否完成，以及用了多长时间。

每条反馈都应包含使用的组合版本、设备和屏幕尺寸、复现步骤、预期结果、实际结果和是否包含敏感数据。请提醒用户不要提交密码、Token、生产数据或其他人的个人信息。问题分级可用阻断、严重、一般和建议；阻断问题优先修复，体验建议进入产品待办。

团队每个迭代回看反馈主题，例如“字段太多”“每周任务流不清楚”“手机上保存按钮难以触达”。将重复反馈和需求编号关联起来，再通过小范围改动、回归测试和版本说明确认问题是否真正解决。这样既能避免单个意见立刻导致大改，也不会让有价值的趋势被忽略。

## 52:00–57:00｜扩展方向与当前边界

**画面**：展示 API 契约、数据库结构、测试矩阵和候选扩展路线。

**旁白**：

未来可以沿三个方向扩展。第一是增加新的前端或 API 实现，但必须先明确它支持哪些接口、认证方式和错误语义，再通过共享契约测试。第二是增强数据分析，例如趋势图和周期对比；新增汇总字段前要先说明统计口径，避免不同客户端给出不同结果。第三是管理员和运营能力，例如用户管理、审计和数据导出，但需要权限设计、隐私策略和相应验收。

还可以讨论提醒、日历同步、团队协作、离线编辑或多语言界面。这些功能会改变数据流、授权边界或产品目标，应先做需求澄清，而不是直接在现有表中临时增加字段。

当前系统不包含消息队列、缓存和第三方同步，也没有声明生产级性能指标。现有 schema 初始化脚本不是通用迁移框架，FastAPI 的多条 SQL 写入也不能假设天然处于一个事务中。架构扩展需要先记录边界，再用测试证明一致性。

## 57:00｜结束

**画面**：回到日、周、月闭环；最后显示文档中心和八个组合。

**旁白**：

总结一下，个人效能系统以日、周、月的实际工作流为核心，用清晰的需求、共享的数据语义、可替换的技术实现和可追踪的验收方法支撑交付。发布不是终点，只有把用户反馈转化为优先级、验证和下一轮改进，系统才会持续符合真实需要。
